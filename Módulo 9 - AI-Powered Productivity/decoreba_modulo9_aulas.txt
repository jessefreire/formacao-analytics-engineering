A DIFERENCA FUNDAMENTAL DO AI/BI
--------------------------------------------
Power BI e similares          -> AI/BI Databricks
- relacionamento dim x fato   -> NAO existe modelagem na ferramenta
  modelado na ferramenta
- relacionamentos + DAX       -> UMA QUERY SQL (create from SQL)
- consome o modelo semantico  -> consome o DATASET DA QUERY

Fluxo: data -> add data source -> tabelas do Unity Catalog
       -> create from SQL -> escrever o join

3 habitos:
- COMENTAR os objetivos dentro da query (nao perder de vista as colunas)
- NAO deixar SELECT * -> listar as colunas explicitamente
- APAGAR as tabelas soltas do dataset depois de criar a query

>> dev x prod: a aula demonstra no esquema dev, mas repete que em projeto real
   se usa PRODUCAO - e isso que garante que atualizacao de dado reflita no BI

CALCULOS CUSTOMIZADOS (as "medidas" do AI/BI)
--------------------------------------------
- Criam medida SEM escrever SQL de agregacao
- Quantidade de transacoes -> COUNT(DISTINCT numero_transacao)
- Valor total              -> SUM(valor_transacao)
- Media do valor           -> AVG(valor_transacao)

ALERTAS
--------------------------------------------
>> ALERTA NAO E CRIADO NO DASHBOARD NEM NO WIDGET
   E criado na ABA DE ALERTAS - e antes dele precisa de uma QUERY.

Estrutura da query do exemplo (queda > 50% de um mes pro outro):
  CTE transacoes_dezembro -> conta transacoes distintas do periodo
  CTE transacoes_janeiro  -> conta transacoes distintas do periodo
  CTE percentual          -> join das duas + variacao percentual
  SELECT principal        -> devolve como TEXTO, LIMITADO A UMA LINHA

- A restricao a UMA LINHA e o que permite usar a opcao FIRST ROW na condicao
- Condicao do exemplo: coluna percentual <= -50

>> A DEPENDENCIA QUE QUEBRA O ALERTA
   O alerta NAO dispara fora do agendamento da QUERY. A query precisa ter
   rodado naquele agendamento.
   Agende a query ANTES do alerta: query 17:30 -> alerta 18:00.
   Alerta antes da query nao tem dado pra avaliar.

- Template de e-mail customizavel com HTML e variaveis
- O LINK PRO DASHBOARD NAO E NATIVO no template: incluir a mao
- Dica de teste: aproxime os dois agendamentos pra ver o e-mail chegar

AS 9 BOAS PRATICAS PRA TREINAR A IA
--------------------------------------------
1. DESCRICAO em tabelas e colunas -> traduz termo tecnico em linguagem de negocio
2. Colunas PK/FK explicitas -> pk_agencia x fk_agencia e mais logico que
   "codigo" x "ID"
3. Aba de INSTRUCOES -> define conceito de negocio na SUA definicao
4. SINONIMOS nas colunas -> faturamento e receita na mesma coluna
5. VALUE DICTIONARY em coluna string -> traduz sigla e codigo
6. QUERIES SQL DE EXEMPLO -> ensina regra de negocio muito especifica
7. BENCHMARKING -> mede a qualidade e mostra onde melhorar
8. FEEDBACK em cada resposta -> e o mecanismo de aprendizado
9. MONITORAR o feedback dos usuarios -> evolui o espaco e aumenta a confianca

EXEMPLOS QUE MOSTRAM O PODER DAS PRATICAS 3, 4 E 6
--------------------------------------------
- SINONIMO: em tipo_cliente cadastrar "tipo de cliente", "segmento de cliente",
  "segmento". Depois "qual o segmento que mais transacionou em 2022?" resolve
  pra coluna certa.
- INSTRUCAO: "quantos clientes ativos em 2011?" sem instrucao contou clientes
  DISTINTOS. Com a instrucao "considere ativo quem fez pelo menos uma transacao
  a cada 20 dias", a resposta muda e o SQL aplica a regra.
- QUERY DE EXEMPLO (o caso mais rico): "top performance" nao tem significado
  universal. No BanVic e crescimento em QUANTIDADE e em VALOR, ponderados
  40% quantidade / 60% valor, gerando um SCORE. Sem exemplo, o Genie assumiu
  "maior valor total". Com a query salva, passou a reproduzir a ponderacao.
  Detalhe: COALESCE garante crescimento ZERO quando nao ha ano anterior.

BENCHMARKS
--------------------------------------------
- Perguntas de teste com uma QUERY DE REFERENCIA que voce sabe estar correta
- Ao rodar: o Genie gera o SQL, executa, responde e COMPARA com a referencia
- Serve pra MEDIR A ACURACIA ANTES DE LIBERAR o espaco

>> PEGADINHA: SQL DIFERENTE NAO E ERRO
   Nos 2 testes o Genie escreveu queries distintas e chegou aos MESMOS
   resultados; a diferenca era so formatacao (sem simbolo de %, menos casas).
   Avaliacao boa, acuracia 100%.

>> REGRA DE OURO DO BENCHMARK
   Voce NAO CORRIGE O SQL ali. Voce adiciona CONTEXTO na configuracao
   (query de exemplo e/ou instrucao) e RODA O BENCHMARK DE NOVO.
   E reexecuta os testes sempre que os dados mudarem: coluna nova, tabela
   nova, join novo, dado novo.

CONEXAO COM DESAFIO FINAL (DBT + POWER BI)
--------------------------------------------
- Os 4 objetivos da gerencia de operacoes SAO praticamente o escopo do dashboard
  Power BI deste repo. As paginas "Visao Geral" e "Tipos de transacao" do PBIP
  tem os mesmos nomes e o mesmo recorte.
- O contraste com o Power BI e a licao de ARQUITETURA: aqui nao existe modelo
  semantico com relacionamento e DAX; a juncao e uma query SQL. Sabendo os dois,
  voce ESCOLHE a ferramenta em vez de so operar a que conhece.
- As 3 medidas do AI/BI sao as mesmas do modelo semantico daqui:
  COUNT(DISTINCT) na PK da fato = Qtd Transacoes em DAX; SUM e AVG equivalentes.
- PK/FK explicitas (pratica 2) e argumento a favor da convencao do banvic-dbt:
  nomear pk_agencia / fk_agencia e o que faz uma IA inferir o join certo.
- Descricao de coluna deixou de ser burocracia: os .yml dos models e as
  descricoes no TMDL alimentam qualquer camada de IA por cima.
- Regra de negocio como QUERY DE EXEMPLO e o padrao pra metrica composta do
  BanVic: "agencia top performance" precisa de definicao explicita e versionada.
- RLS na dimensao x na fato e decisao que o dashboard daqui enfrentaria ao ir
  pra producao com dado real.
- Guardrail de dados REFORCADO: a aula mostra o usuario chegando em CPF ou nome
  de cliente via Genie. Protecao tem que estar NO DADO (mascaramento no UC),
  nao em omitir a coluna do visual.
